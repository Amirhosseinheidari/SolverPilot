# راهنمای آزمون فنی گردش‌کار تولید

این پوشه شامل یک مثال آموزشی عمومی با ذکر منبع، یک نمونهٔ مصنوعی برای بررسی کمبود ظرفیت، و فرم‌های خالی بازخورد است. اجرای این فایل‌ها یک آزمون فنی تکرارپذیر است؛ به‌تنهایی پایلوت با کاربر واقعی، تجربهٔ مشتری یا شاهد صرفه‌جویی در وقت انسان محسوب نمی‌شود. هیچ بازخورد یا نتیجهٔ مصاحبه‌ای در این پوشه ثبت نشده است.

## داده‌ها و جواب مرجع

دادهٔ پایه در [nd-production.json](nd-production.json) از مدل عددی [بخش ۲.۱.۴ کتابچهٔ ND Pyomo Cookbook اثر Jeffrey C. Kantor](https://jckantor.github.io/ND-Pyomo-Cookbook/notebooks/02.01-Production-Models-with-Linear-Constraints.html#production-plan-mixed-product-strategy) اقتباس شده است. [مخزن رسمی پروژه](https://github.com/jckantor/ND-Pyomo-Cookbook) این مجموعه را محتوای آموزشی تهیه‌شده در دانشگاه نوتردام معرفی می‌کند. تغییرات سناریوهای این پوشه را خودمان برای آزمون ساخته‌ایم؛ این تغییرات دادهٔ عملیاتی یک شرکت نیستند.

| سناریو | مقدار X | مقدار Y | سود هفتگی، دلار | توضیح |
| --- | ---: | ---: | ---: | --- |
| baseline | 20 | 60 | 2600 | جواب مرجع منتشرشده |
| more-labor | 10 | 80 | 2800 | ظرفیت منابع [90,100] |
| tighter-capacity | 30 | 40 | 2400 | ظرفیت منابع [70,100] |
| changed-prices | 0 | 80 | 3200 | سود واحد محصولات [30,40] |
| reset | 20 | 60 | 2600 | بازگشت پارامترهای ذکرنشده به مقدار پایه |

برای بررسی مستقل جواب پایه، از دو محدودیت ظرفیت داریم:

`40X + 30Y = 20(X + Y) + 10(2X + Y) <= 20*80 + 10*100 = 2600`

نقطهٔ `(20,60)` همهٔ محدودیت‌ها را رعایت می‌کند و همین سود را به دست می‌آورد. این استدلال حسابی کوچک، مرجع مستقل همین مسئله است و سطح گواه عددی صادرشده در زمان اجرای حل‌گر را تغییر نمی‌دهد.

در فایل [synthetic-minimum-commitments.json](synthetic-minimum-commitments.json)، حداقل تولید هر محصول را به‌صورت مصنوعی ۱۰ واحد گذاشته‌ایم. جواب پایه و سناریوی reset همچنان `(20,60)` با سود ۲۶۰۰ است. در سناریوی shortage ظرفیت نیروی کار A فقط ۵ است، درحالی‌که حداقل تعهدها دست‌کم ۲۰ واحد از این منبع می‌خواهند. انتظار داریم ناسازگاری ظرفیت گزارش شود؛ این مورد نباید به‌عنوان جواب پذیرفته‌شده با سود صفر نمایش داده شود. حداقل تعهدها و این کمبود در منبع اصلی وجود ندارند و از کاربر واقعی دریافت نشده‌اند.

## اجرا و بازاجرایی

فایل بستهٔ پایلوت را از حالت فشرده خارج کنید و PowerShell را در ریشهٔ همان پوشه باز کنید. این بسته شامل wheel آزمایشی، فایل نسخه‌های وابستگی‌ها (`runtime-lock.txt`)، داده‌ها و برنامهٔ اجراست. شمارهٔ بسته فعلاً 0.4 است، اما این ساختِ توسعه با نسخهٔ منتشرشدهٔ PyPI تفاوت دارد؛ فایل wheel داخل همین بسته را نصب کنید. فایل `SHA256SUMS.json` اثرانگشت فایل‌ها را ثبت می‌کند و امضای دیجیتال نیست.

با Python 3.12، بدون فعال‌سازی یا تغییر محیط‌های قبلی، این فرمان‌ها را اجرا کنید:

```powershell
py -3.12 -m venv .pilot-origin
.\.pilot-origin\Scripts\python.exe -I -m pip install -r runtime-lock.txt .\solverpilot-0.4-py3-none-any.whl
.\.pilot-origin\Scripts\python.exe -I benchmarks/qualify_production_workflow.py run --input docs/pilot/nd-production.json --output public-trial --repeats 6 --include-model

py -3.12 -m venv .pilot-replay
.\.pilot-replay\Scripts\python.exe -I -m pip install -r runtime-lock.txt .\solverpilot-0.4-py3-none-any.whl
.\.pilot-replay\Scripts\python.exe -I benchmarks/qualify_production_workflow.py replay --study public-trial/study.json --output independent-replay.json
```

پوشه‌ها و فایل‌های خروجی باید تازه باشند؛ برای اجرای بعدی نام دیگری انتخاب کنید. مشخصات wheel، نسخه‌های وابستگی‌ها و شواهد خروجی را کنار هم نگه دارید. نصب editable از سورس یا نصب نسخه‌ای دیگر، شاهد ارزیابی همان wheel نیست. راهنمای [انگلیسی](README.md) فرمان بررسی خودکار دو نصب تمیز و معادل مسیرهای لینوکس و مک را هم دارد.

موفقیت `technical_gate_passed` در برنامهٔ گردش‌کار فقط توافق با مرجع و بازاجرایی در همان محیط را نشان می‌دهد. بررسی نصب تمیز، گزارش جداگانهٔ `qualification.json` در ریشهٔ خروجی ابزار نصب دارد. هیچ‌کدام بازخورد انسانی یا تأیید نیازهای یک کسب‌وکار واقعی نیستند.

برای هر اجرا یک مسیر خروجی تازه انتخاب کنید:

```powershell
python benchmarks/qualify_production_workflow.py run --input docs/pilot/nd-production.json --output NEWDIR --repeats 6 --include-model
python benchmarks/qualify_production_workflow.py replay --study NEWDIR/study.json --output NEWJSON
```

برای نمونهٔ مصنوعی از پوشه‌ای دیگر استفاده کنید:

```powershell
python benchmarks/qualify_production_workflow.py run --input docs/pilot/synthetic-minimum-commitments.json --output NEWDIR-SYNTHETIC --repeats 6 --include-model
```

عبارت‌های `NEWDIR`، `NEWJSON` و `NEWDIR-SYNTHETIC` جای‌نگهدار مسیرهای محلی تازه هستند. گزینهٔ `--include-model` ورودی کامل قرارداد و مدل موردنیاز برای بازاجرایی را در خروجی می‌گذارد. پیش از اشتراک‌گذاری، داده‌ها، برچسب‌ها و تصمیم‌های خروجی را بررسی کنید. این فرمان‌ها بازخورد انسانی تولید نمی‌کنند.

بازاجرایی را با همان wheel و همان نسخه‌های دقیق وابستگی‌ها انجام دهید. بازاجرایی یک حل تازه با شناسهٔ جدید و پیوند به اجرای قبلی است. جزئیات اعتبارسنجی منبع، نسخه‌ها، صدور خروجی و حدود شواهد در [مستند گردش‌کار](../PRODUCTION-EVIDENCE-WORKFLOW.md) آمده است.

زمان‌های ثبت‌شده، زمان اجرای نرم‌افزار در همان محیط هستند. شش بار تکرار، شاهد سریع‌تر بودن از ابزار دیگر، صرفه‌جویی در وقت انسان، فهم کاربر یا مقیاس‌پذیری صنعتی نیست. اگر خروجی مراحل را جدا می‌کند، هزینهٔ آماده‌سازی، کامپایل، حل، اعتبارسنجی و گزارش‌سازی را با یکدیگر اشتباه نگیرید.

## محدوده و تفسیر

این مدل مقدار تولید پیوسته را با سود واحد خطی بیشینه می‌کند. مصرف منابع و ظرفیت‌ها نامنفی‌اند و حداقل و حداکثر تولید ثابت است. حداکثر X برابر ۴۰ است و رشتهٔ `"inf"` در JSON یعنی Y کران بالای محدود ندارد. مدل شامل دسته‌های صحیح تولید، هزینهٔ راه‌اندازی، موجودی، زمان تأمین یا تصمیم‌گیری تصادفی نیست. واحدها را کاربر مشخص می‌کند.

تطابق فرمول‌بندی با قرارداد، بررسی مستقل جواب نسبت به قرارداد، و شواهد بهینگی عددی سه موضوع متفاوت‌اند. پذیرفته‌شدن جواب به معنای کامل‌بودن همهٔ نیازهای واقعی کسب‌وکار نیست. وقتی ضرایب سود تغییر می‌کنند، اختلاف سود نسبت به پایه عمداً ارائه نمی‌شود، زیرا تعریف تابع هدف عوض شده است. خطای ورودی، عدم امکان تحقق محدودیت‌ها و نبود جواب نباید به سود صفر تبدیل شوند.

## ثبت بازخورد واقعی

از [feedback-template.md](feedback-template.md) یا [feedback-template.json](feedback-template.json) یک کپی جداگانه تهیه کنید. همهٔ پاسخ‌ها در ابتدا `null` هستند؛ یعنی هنوز پاسخ یا اندازه‌گیری دریافت نشده است. اطلاعات نامعلوم را خالی نگه دارید و فقط گفته‌ها یا مشاهدات واقعی مشارکت‌کننده را ثبت کنید.

می‌توان از مشارکت‌کننده خواست گزارش را بخواند، یک تصمیم و یک کمبود ظرفیت را با زبان خودش توضیح دهد، و نیازهای غایب در قرارداد را مشخص کند. زمان روش دستی را فقط هنگامی ثبت کنید که شخص واقعاً آن کار را با شرایط توصیف‌شده انجام داده یا اندازه گرفته باشد. زمان اجرای ماشین را به صرفه‌جویی در کار انسانی تبدیل نکنید. برای شناسهٔ مشارکت‌کننده می‌توان از نام مستعار استفاده کرد؛ اشتراک‌گذاری بازخورد نیازمند تصمیم صریح خود اوست.
